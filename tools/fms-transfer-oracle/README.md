# fms-transfer-oracle: Import and Export Records on FileMaker Server

A research tool for `om-transfer` (script-steps.md, "Implementation notes
(import/export)"). The script harness (`tools/fms-script-harness`) has
libFMEngine's shared runtime, where Import Records (35), Export Records
(36), Save Records as Excel (143) and Export Field Contents (132) return
error 3: their handlers are fmsased's (`FMS::SASEScriptRuntime::DispatchStep`,
script-runtime.md 10.2), which the harness cannot load. This tool runs
probe scripts on a real FileMaker Server instead: the lab FileMaker
Server (26.0.3), with the maintainer's approval of 2026-10-29 for a
separate probe database only. Export Records also runs offline: with
`DOCUMENTS` the harness runs step 36 the way fmsased does (its README),
and x01 run that way gave the lab server's files. Battery x05 ran there.

## Pieces

| file | what it does |
|---|---|
| `probe_schema.py` | adds the probe fields to the Contacts starter template's saveAsXML (number, date, time, timestamp, repeating, stored and unstored calculations, summaries of every operation and option with a break field `B` and a weight `W`, a global, auto-enter calculations, validated fields), optionally taking the AccountsCatalog of another schema document |
| `build.sh <battery>` | builds the probe database for a battery: the schema above plus the battery's scripts, generated by FMUpgradeTool and scanned by FileMaker's ScanScript in the harness container (`runbat.sh` with `SCHEMA`); prints the built file |
| `run_fms.py` | `upload` (Admin API, as `OM_Probe_ImportExport.fmp12`, opened), `put` (import sources to the Documents folder over SSH, `omprobe_*` names only), `run <script>` (one schedule, run and waited for), `fetch <dir>` (the Documents folder's `omprobe_*` files, then deleted there), `cleanup` (schedule, database and files removed) |
| `gen_x02.py` | writes battery x02 and its sources |
| `gen_x05.py` | writes battery x05 |
| `batteries/` | x01 exports, x02 imports, x03 exports (related records, typed values, groups, Excel, dBase), x04 imports (update matching by index keys, updates into another table than the window's; hand-written), x05 exports of summary fields (every operation and option, repeating summaries, sorted and unsorted, with and without groups, the script engine's own values for comparison) |
| `sources/` | the import sources, copied to the server's Documents folder before a run |
| `results/x05/` | x05's files, from FileMaker Server's engine in the script harness |

The probe steps use the Export Records, Import Records and Sort Records
builders of `tools/fms-script-harness/make_patch.py` (the XML shapes
FileMaker's own Save as XML writes; settled by writing a step from
script-steps.md 11.3-11.5 into a scratch file and reading FileMaker's
rendering of it). FileMaker's XML importer stores the import field
delimiter attribute literally and the field names row 0-based (`Names: N` in
the probe syntax is 1-based).

Results of x01-x04 are in `crates/om-transfer/tests/data/x0N/`; the tests
there replay every probe. x05's are in `results/x05/`.

The x05 results were collected with the schema generator at commit `12e41ac4` of the
earlier, private history.
It wrote noncanonical defaults for some omitted summary options, relying
on importer fallbacks. The corrected generator emits explicit defaults
and has been checked locally as XML; it has not been rerun in the engine.
The committed files remain the original engine observations.

## Running

```sh
export FMS_ROOT=/path/to/re/extracted/fms/deb/opt/FileMaker FILES=/path/to/files WORK=/path/to/scratch \
       HARNESS_LOCK=/path/to/re/work/fms-harness/.run.lock
# FileMaker Server opens no file whose full access account has no password:
# lend the AccountsCatalog of a saveAsXML of a file with one (kept in $WORK).
export ACCOUNTS_XML=$WORK/test-project.xml
F=$(tools/fms-transfer-oracle/build.sh tools/fms-transfer-oracle/batteries/x01-export.txt)
python3 -I tools/fms-transfer-oracle/run_fms.py upload "$F"
python3 -I tools/fms-transfer-oracle/run_fms.py put tools/fms-transfer-oracle/sources/x02/*   # imports
python3 -I tools/fms-transfer-oracle/run_fms.py run Run
python3 -I tools/fms-transfer-oracle/run_fms.py fetch /tmp/x01
python3 -I tools/fms-transfer-oracle/run_fms.py cleanup
```

Exports in the script harness, without a server. `Get ( DocumentsPath )`
is empty there, so x05 falls back to `/root/Documents/`, where `DOCUMENTS`
is mounted:

```sh
WORK=/tmp/x05 FILES=/path/to/files FMS_ROOT=... HARNESS_LOCK=... \
    tools/fms-transfer-oracle/build.sh tools/fms-transfer-oracle/batteries/x05-export-summaries.txt  # once, for $WORK/probe-en.xml
mkdir -p /tmp/x05-docs
DOCUMENTS=/tmp/x05-docs SCHEMA=/tmp/x05/probe-en.xml WORK=/tmp/x05 FILES=... FMS_ROOT=... HARNESS_LOCK=... \
    tools/fms-script-harness/runbat.sh tools/fms-transfer-oracle/batteries/x05-export-summaries.txt contacts-en.fmp12 /tmp/x05-out
```

The container writes `DOCUMENTS` as root. Run on the lab server, x05
needs no other change.

Credentials come from the project `.env` (`OM_ENV` names another file;
the default is the `.env` at the repository root) and are never printed or
logged; `OM_PROBE_LOG` collects every Admin API call and SSH command.

## Findings that shaped the probes

- Relative export paths (`file:name`) go to the session's temporary folder
  (`/tmp/S<n>/` on Linux), which FileMaker Server deletes when the script
  ends: probes export to `Get ( DocumentsPath )`.
- A path outside the Documents and temporary folders is error 800.
- The XML source of an Import Records step from XML is stored in the
  profile (without variable expansion); the probe's import of one did not
  resolve on the server (717).
